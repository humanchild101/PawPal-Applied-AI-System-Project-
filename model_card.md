# PawPal+ Project Reflection

## Limitations and Biases
The limitations of this system is that it does not hold the user accountable if they enter 0 available minutes for a day. The application cannot do much to change the user's decision. It can only still suggest a schedule that also contains a warning that the user does not have enough available time. The suggestions that are provided for conflicts also need some improvement because often, it is to 'increase the available time', when that depends entirely on the user. The system does not make enough smart suggestions to change the duration of certain tasks, but that may require the addition of additional knowledge or a model to know what tasks are considered generally 'important' regardless of the user's decision on how important each task is. 

## Misuse and Prevention
Despite the AI being used for the answering schedule questions and resolving schedule issues, the user can still ask it irrelavent questions and it *will* answer. I asked it a question about apples, but a user could ask it questions for any malicious intent, and if the question is framed right, it will answer. This could be resolved by adding additional guardrails like writing specific rules for the AI to follow. Perhaps using a large library of valid questions and phrase ordering could be another solution. 

## Surprising Aspects
It really surprised me that the AI was able to give such detailed responses using specific aspects of the scheduling context. It tuned its response to the user's specific schedule when giving an answer to a question, and it was not a generic response at all. This was very interesting to see.

## AI Collaboration
I used Claude as a tool to suggest and implement while working on this project. One suggestion it gave that was useful was to add the secrets.toml file where my API key is to .gitignore so it wouldnt get committed. I was unsure of how a user could run the app if they didn't have that file, so it suggested that I create an example file so that the user can copy paste the details of the file into their own manually created secrets.toml file along with their manually generated API key. It's very inefficient for real world projects, but for now, this seemed to be a good solution. One flawed suggestion Claude gave was involving an intitial design suggestion. I wanted to implement RAG and agentic workflow, and one of its suggestions was to create an 'agentic' model that only answered questions. Its logic was that it would have been agentic because it planned its responses based on the information it retrieved, which could be true, however, such a feature did not seem to have much use in the program and did not seem to be truly agentic either if it was not performing tasks for the program instead of just 'planning responses'
